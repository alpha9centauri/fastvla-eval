# Step 3 — integration: built, not yet planning. Where it stands.

Author: Varun Chandra, 2026-10-19. **Step 3 is incomplete.** This file records exactly what works,
what does not, and what has been ruled out, so the next session does not repeat the search.

## What is done

`route.py` is the whole integration surface, and it is the right surface.
`dgcore.generate_demo` calls the route planner exactly once:

```python
wp, detours, shape = plan_detours(sg, obstacle, wp0, ceiling=ceil)
```

`install("curobo")` binds `plan_detours_curobo` over `dgcore.plan_detours` at runtime.
**dgcore.py is not edited and nothing is copied out of it.** `PLANNER=script` installs nothing and
keeps the scripted planner; `PLANNER=ompl` raises rather than pretending to exist (step 1 never
needed the fallback). The replacement returns `(wp, detours, shape)` with the keys dgcore's caller
reads, so grasp/place primitives, the OSC executor, the 2 cm GJK certification, the replay gate and
the writer are all untouched and all still run.

Verified working inside `dgcore.generate_demo` on a real eval-rule oa1 scene:

- the planner is reached and the scene is built (19.26 cm shift applied)
- the world is assembled from the labeler's hulls (step 2) and loaded into cuRobo
- the tool offset is calibrated from the live arm: **0.0965 m along the hand's +z**, constant
- start IK succeeds and the route-stage returns a clean, correctly-named rejection

## What does not work

`MotionGen.plan_single` returns `MotionGenStatus.IK_FAIL` on the goal pose, in ~0.7 s, on every
attempt and every hand-off height. No joint path is produced, so no demo has yet been generated by
this route.

## Ruled out, with the measurement that ruled it out

| hypothesis | test | result |
|---|---|---|
| goal pose unreachable | standalone `IKSolver`, `rotation_threshold` 0.05→3.2, `num_seeds` 16/64, self-collision on and off | **solves at 0.0 mm position error and 0.000 rotation error in every configuration** |
| joint limits differ between the models | printed MuJoCo `jnt_range` against cuRobo's `get_joint_limits` for all 7 joints | **identical to 4 decimals** |
| wrong end-effector frame | calibrated cuRobo `panda_hand` against robosuite's `gripper0_grip_site` at the scene's own qpos | real, found and fixed: 9.65 cm along hand +z. Was making every goal ~10 cm too far out |
| quaternion convention | compared MuJoCo `robot0_eef_quat` (xyzw) with cuRobo `ee_quaternion` (wxyz) at the same qpos | real, found and fixed: conversion added both ways; orientations now agree to 4 decimals |
| obstacle margin at the terminal | `PLANNER_ACTIVATION_M` 0.04 → 0.02 → 0.01 → 0.005 | **no change at any value** — so not the margin, despite pre_place sitting 2.35 cm from the bottle |
| `MotionGen.solve_ik` after graph capture | replaced with a dedicated `IKSolver` | real, found and fixed: after `warmup(enable_graph=True)` an ad-hoc `solve_ik` fails with *"changing goal type, cuda graph reset not available"*, which cuRobo surfaces as `IK_FAIL`. Router IK works now; `plan_single`'s internal goal IK still does not |
| goal Pose built from numpy vs built by cuRobo | mirrored step 1's working call, `compute_kinematics(...).ee_pose.clone()` | **no change** |

## The next thing to test, and why

Step 1's feasibility script — which planned 20/20 successfully — built `MotionGen` with a
**non-empty world at construction** and never called `update_world`. `route.py` builds with an
empty `WorldConfig()` plus a sized `collision_cache` and then calls `update_world(meshes)` per
scene, because step 1 also measured 11.3 s of warmup against 0.2 s per plan and rebuilding per
demo would dominate the run.

So the leading hypothesis is that **`update_world` on a MotionGen constructed with an empty world
leaves the mesh world wrong** — for instance every mesh at the origin, enveloping the arm — which
would make every goal look blocked and would explain why the activation distance makes no
difference at any value. That is directly testable in one run: after `update_world`, query
`get_collision_distance` at the retract configuration, which is far from everything in these
scenes. A collision there proves the world is corrupt rather than the goal unreachable.

If that is it, the fix is to construct `MotionGen` with the first scene's real world and then
`update_world` for subsequent scenes, or to rebuild per scene and accept the 11.3 s (which at ~197
scenes would add about 37 minutes — tolerable, and measurable either way).
